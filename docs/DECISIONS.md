## ADR-0001 · 2026-10-18 · Project lives at `rea/p3fes-port/` as its own nested git repo
**Context.** GOAL.md and the disc image were placed in `C:\Users\Ash\Downloads\rea`, which is a clone of the REA tool's upstream repo (`morluto/rea`, branch `main`). GOAL.md requires frequent commits and a repo holding only our code. The user created `rea/input/` for the ISO, signalling this workspace is the intended working folder.
**Decision.** Create `rea/p3fes-port/` with its own `.git`. Move the ISO into `p3fes-port/input/`. Add `p3fes-port/` and `GOAL.md` to the REA clone's `.git/info/exclude` (local, not its tracked `.gitignore`).
**Why not alternatives.** Committing into the REA clone pollutes a third-party project's history and breaks future `git pull`. A sibling directory outside the IDE workspace would be invisible to the user day-to-day.
**Consequences.** Git doesn't descend into nested repos, so REA's status stays clean. Cheap to reverse: it is a directory move.

## ADR-0002 · 2026-10-18 · REA for static ELF inspection only; IDA Pro driven directly for all R5900 work
**Context.** GOAL.md asks for REA (static record/memory map/inventory) and "IDA Pro via the IDA hook/MCP" as the primary surface. REA's own source gates MIPS out of every engine path: `src/ida/IdaProvider.ts:107-128` returns `architecture_unsupported` — *"REA's IDA adapter has no verified MIPS lane"*; `src/ghidra/GhidraProvider.ts:647` admits only x86/x86-64/ARMNT/ARM64 PE on Windows; stock Ghidra 12.1.4 has no R5900 SLEIGH at all. REA rejected the ISO outright (`unsupported binary format`). IDA Pro 9.3 itself ships `r5900l`/`r5900b` in `procs/mips.dll`.
**Decision.** Use REA's provider-independent `inspect_binary_layout` (ELF32 MIPS metadata path exists in `src/application/MipsElfMetadata.ts`) for the Phase 0 static record. Drive IDA Pro directly through idalib (`import idapro`, venv `C:\Users\Ash\.local\share\rea\ida-mcp`) and/or its own `idalib-mcp` MCP server — this *is* "IDA via MCP", just not routed through REA.
**Consequences.** Evidence provenance for disassembly comes from IDA exports we write ourselves (`tools/ours/ida/`), not REA Evidence records. If REA later grows a MIPS lane, revisit.

## ADR-0003 · 2026-10-18 · Toolchain: MSVC 14.44 primary, clang-cl 22 kept green, CMake + Ninja, C++20, D3D11 first
**Context.** Installed: VS 2022 Build Tools 17.14 (MSVC 14.44.35207), LLVM 22.1 clang-cl, CMake 4.3.1, Ninja, Windows SDK 10.0.26100 (d3d11.h, xaudio2.h present). No vcpkg.

## ADR-0004 · 2026-10-18 · The recompiler consumes IDA disassembly, never Hex-Rays pseudocode
**Context.** `hexmips.dll` contains no `R5900`, `MMI`, `COP2`, `VU0` or MMI-mnemonic strings. The Emotion Engine's 128-bit MMI (`paddw`, `pextlw`, `lq`/`sq`…) and VU0 macro-mode COP2 ops are exactly the hot paths a port must get right.
**Decision.** Phase 3's recompiler walks IDA's function boundaries and raw instruction stream (`ida_ua.decode_insn` / `idc.GetDisasm`), emitting C++ per instruction. Pseudocode is for human reading in Phase 5 only.
**Consequences.** Need our own R5900 instruction table in `recomp/` (MIPS III + MMI + COP0/1/2). Unit-test MMI/FPU translations against PCSX2 (Phase 4).

## ADR-0006 · 2026-10-18 · Tooling verdicts after acquisition: own CVM extractor, no Sony-derived FLIRT sigs, Ghidra EE extension as a second-opinion decompiler
**Context.** The acquisition pass (`docs/TOOLS.md`) raised four questions. (1) `cvm_tool` builds and independently confirms the CVMs are unencrypted `ROFSBLD 1.52` images, but half of it (roxfan's part) carries no license. (2) The only known PS2 SDK FLIRT signature set is a 2018 forum attachment derived from Sony's `libsce*` with no license. (3) `ghidra-emotionengine-reloaded` v2.1.38 (Apache-2.0, built for Ghidra 12.1.4) ships a real `r5900:LE:32:default` SLEIGH — unlike IDA's `hexmips.dll`, its decompiler understands MMI and VU0 macro-mode. (4) Three community P3FES decomp/recomp projects exist on GitHub, unevaluated. Also: the ps2dev v2.0.0 prebuilt EE toolchain compiles and links a valid R5900 ELF on this host.
**Decisions.**
1. **CVM extraction uses our stdlib extractor** (`tools/ours/cvm/cvm_extract.py`); `cvm_tool` is a read-only cross-check, never part of the pipeline. The format is 0x1800 header + ISO9660, so a dependency with licensing doubt buys nothing.
2. **The Sony-derived signature pack is not acquired.** Provenance is Sony SDK libraries and the pack is unlicensed; sce* labelling is done from `ps2sdk` headers, prologue/behaviour matching in IDA, and community *facts* (addresses, not files). The user may override this; if so, it goes under `tools/third_party/ida-sigs/` (gitignored) with the provenance recorded in TOOLS.md.
3. **Install the Ghidra EE extension** into the user's Ghidra (`Ghidra/Extensions/`) and keep a headless Ghidra project at `ghidra/` (gitignored) as a **second-opinion decompiler** for MMI/VU0-heavy functions in Phase 5. This does *not* supersede ADR-0004: the recompiler still consumes IDA disassembly, and IDA (`symbols/p3fes.sym`) stays the sole naming authority — Ghidra names are never copied back as truth.
4. **Community projects are evaluated read-only first** (`docs/COMMUNITY.md`); adoption of any code or symbol file is a separate, license-gated decision recorded as its own ADR.
5. The EE toolchain makes **compiled test vectors** viable for Phase 4 (small R5900 programs run under PCSX2 and under our recompiler, traces diffed) — adopt that as the MMI/FPU unit-test strategy.
**Consequences.** Two decompilers, one authority. PCSX2 remains inert until the user supplies a BIOS. Amicitia (no license) is reference reading only.

## ADR-0007 · 2026-10-18 · User override: acquire the unlicensed PS2 SDK FLIRT pack for private use, if it measurably helps
**Context.** ADR-0006 item 2 declined the 2018 community FLIRT pack (Sony SDK 1.0.0–3.0.3, libsn, CodeWarrior; no license; derived from Sony libraries). The user directed: *"use the unlicensed ps2 pack if its better."* Hand-labelling `sce*` functions is slow and error-prone; the game targets SDK 3.1.x, so a 3.0.3 pack should match a large, stable subset (libkernel, libc, libgraph, libdma, libpad, libmc, libcdvd, libsif*).
**Decision.** Supersedes ADR-0006 item 2. Acquire the pack **for private use on this machine only**: downloads and extracted `.sig` files live in gitignored `tools/downloads/` and `tools/third_party/ida-sigs/`; installation goes to IDA's *user* signature directory (`%APPDATA%\Hex-Rays\IDA Pro\sig\mips\`), never into Program Files. Provenance (original thread, archive capture, mirror, SHA-256 per file) is recorded in `docs/TOOLS.md`; `tools/fetch_tools.ps1` gains an **opt-in** `-IncludeUnlicensedSigs` step so the default fetch stays clean. The pack is never committed, redistributed, or copied into `docs/`/`symbols/`.
**"If it's better" test.** Apply the sigs in IDA and record per-signature match counts plus a spot-check against evidence (`docs/ANALYSIS/05_flirt.md`). FLIRT-derived names are marked as *derived* in `symbols/p3fes.sym`; ELF symbols and manual names win on conflict. If matches are negligible or spot-checks show false positives, the pack is kept installed but demoted to "hint only" and this ADR is amended with the numbers.
**Consequences.** `sce*` naming accelerates from the first analysis pass. The repo's own license posture is unchanged because nothing derived from the pack is tracked; names *we* assign in IDA after verifying behaviour are our own facts about the binary.
**Result (2026-10-18, `docs/ANALYSIS/05_flirt.md`).** Acquired from Wayback captures (TOOLS.md); 7 sigs installed, `PS2SDK_2.0.0` withheld (74 % x86). Pass: 1,348 functions named; audit (`tools/ours/ida/flirt_audit.py`) stripped 242 collisions from the pack's bundled x86 host libraries and placeholders; **1,184 derived names remain, 682 `sce*` total, 773 in the SDK band, 0 false-positive classes left.** Verdict: *better* — the pack stays, names stay tagged `flirt`/derived.

## ADR-0008 · 2026-10-18 · File-I/O HLE hooks at the sector level first; parsers prioritised by bytes covered
**Context.** Phase 1 extraction (`docs/DISC_LAYOUT.md`) established: the three CVMs are 0x1800-byte CRI headers + plain ISO9660 (`offset = 0x1800 + lba·2048`), and **the ELF embeds the complete ROFS directory tree of all three volumes** (149 `#DirLst#` tables, 12,016/12,019 entries matching the extracted manifest) — the game resolves path → LBA from baked-in tables and the disc is only ever read by sector. Format census: 61 % of `DATA` is 41 Sofdec `.SFD` videos; models are **RenderWare** streams (`.RMD`, libraryID `0x1C020037`); ~3,000 "containers" (`.PAC/.BIN/.FPC/.CPK/.SE/.PAK`) are Atlus name-first PAKs (252-byte name + u32 size; `.CPK` is *not* CRI CPK).
**Decisions.**
1. **Sector-level first.** The runtime's CDVD HLE serves `sceCdRead(lba, n, buf)` directly from the extracted CVM files (or the user's ISO) using `offset = 0x1800 + lba·2048`, per volume. No path parsing, exactly reproduces the retail data path, and is testable byte-for-byte. A **path-level hook** at the game's CRI `ROFS_Open` layer is deferred until asset replacement (widescreen UI, texture packs) needs it; when added it must *shadow the in-ELF `#DirLst#` table*, not just the disc.
2. **`extracted/manifest.json` is the authoritative path ↔ LBA ↔ size map** for tooling and tests (gitignored; regenerated by `tools/ours/cvm/cvm_extract.py`). The unknown `#DirLst#` record byte +13 is resolved in Phase 2 topic 11 (`rofs_dir.c` lookup in IDA) before any ROFS emulation.
3. **Parser priority (Phase 1, `runtime/formats/`):** name-first PAK → BF (`FLW0`) / BMD (`MSG1`) via Atlus-Script-Tools knowledge → TMX → RenderWare RMD stream chunking → ADX/AFS → PM1 → SPD/TB → everything else (`.BED`, `.CIN`, `.MAP`, `.TBL`, `.FLD`) stays `unknown` until Phase 2 names the loader that consumes it. Sofdec `.SFD` playback is a Phase 6 concern (decoder, not parser).
**Consequences.** Milestone 1 of Phase 3 ("first `sceGsSetDefDispEnv`") needs only the sector-level HLE. RenderWare in the ELF is a major Phase 2 target: `rw*` engine code and its GS pipeline likely sit under the `G3_2D*` renderer band, which reshapes the VU1/GS census plan (topic 14) toward "which RW pipelines are used".

## ADR-0009 · 2026-10-18 · Community symbol maps are private hints; the committed `.sym` carries only verified or permissively-licensed names
**Context.** `docs/COMMUNITY.md`: **snaku/Persona3-FES-Decompilation** is a splat matching decomp (MWCCPS2 3.0 for game code) whose `checksum.sha1` equals **our exact ELF**; 14,702 symbols (3,060 descriptive), 574 module groups spanning RenderWare 3.7 / Sony SDK / CRI; unmerged PR #4 (TGE, 2026-10-16) adds 16,004 symbols with 8,776 descriptive names plus RW/SCE struct headers and IDA/Ghidra export scripts — **no license** (all rights reserved by default). **poopoocacacacaca/p3fes-recompiled** (GPL-3.0, AI-generated) ships a map 99 % identical to snaku's (doubly encumbered) and targets a *different* ELF (SHA-1 `7ca061aa…`, a "deinterlaced" image). **Virtual-AK/fes-pc-recomp** (MIT) contributes address-level findings (VU1 microcode `0x5A0000–0x77xxxx`, 181 programs; file layer `0x100D80` over `cvFs*` at `0x555B10+`; VBlank handler `0x4D47F0`; BF COMM table at `0x7B92B0`) and format docs. The user's standing stance (ADR-0007) accepts unlicensed resources for private use when measurably better, provided nothing from them is committed or redistributed.
**Decision.**
1. Community maps are cloned into gitignored `symbols/hints/<source>/` and imported into the master IDA database as **hints** carrying a `source` tag (`snaku`, `tge-pr4`, `fes-pc-recomp`); a gitignored `symbols/p3fes.hints.sym` exports them for local use.
2. The committed `symbols/p3fes.sym` includes a community-derived name only when **(a)** its source is permissively licensed (fes-pc-recomp, MIT — attributed in `symbols/README.md`), or **(b)** we have verified the function's behaviour in IDA and recorded the evidence in `docs/ANALYSIS/` — at that point the name is our own fact about the binary and the hint merely told us where to look. Promotion is explicit (`verified` field), never bulk.
3. GPL-3 code is never adopted (it would relicense the port); p3fes-recompiled's 205 HLE stub bindings and its `keep_guest` list for sceIpu/sceMpeg are consulted as a *checklist* only.
4. RW 3.7 / SCE struct headers from PR #4 are consult-only; our headers are written from public RenderWare SDK knowledge, ps2sdk, and our own IDA type recovery.
**Why not alternatives.** Bulk-committing 8,776 unlicensed names would be fast but hard to purge once they propagate into `game/` code and docs; ignoring them wastes a ground-truth map of our exact binary. Hints + explicit promotion is cheap to reverse either way — which is also why this was decided rather than escalated.
**Consequences.** Phase 2/5 naming velocity rises immediately; the promotion rule *is* the Phase 5 hand-decompile queue. The recompiler-base question (MIT `ps2-web-recomp` vs from-scratch) is separate → `docs/RECOMP_OPTIONS.md` → ADR-0010. Hash note: our ELF matches snaku's; p3fes-recompiled's differs by image variant, not region.

## ADR-0010 · 2026-10-18 · `recomp/` is our own per-function recompiler in the N64Recomp shape; `ps2-web-recomp` (MIT) is the semantic reference and second oracle; GPL `PS2Recomp` is consult-only
_User decision 2026-10-18 (asked because it is expensive to reverse and could reasonably have gone the other way); adopted from the draft in `docs/RECOMP_OPTIONS.md` §7._
**Context.** `docs/RECOMP_OPTIONS.md` evaluated four bases against ADR-0003 (MSVC primary, D3D11), ADR-0004 (IDA boundaries + raw instructions), ADR-0009 §3 (no GPL) and Phase 5 (per-function replacement under `tracediff`). `snuri00/ps2-web-recomp` (MIT, 1,068 ★, created 2026-10-08) has complete R5900 semantics — 128-bit MMI (`runtime/include/ps2/mmi.hpp`), two HI/LO pairs, bit-level EE FPU (`fpu.hpp`), VU0 macro + micro, likely branches, `SetSyscall`-aware kernel, IOP R3000 interpreter running IRX, IPU, SPU2, VU1 with pipeline timing — and reportedly runs `SLUS_216.21` to the dormitory 3D scenes with 0 unhandled syscalls (fes-pc-recomp, text only, unverified). But it emits clang-only C++ (`[[clang::musttail]]`, GNU `vector_size`) in 16 KiB units with `switch(entry)` dispatch, re-discovers functions itself and ignores sizes, and its GS is WebGPU compute. `ran-j/PS2Recomp` (GPL-3.0; base of `p3fes-recompiled` together with GPL `god-of-war-recomp` and PCSX2 GS) is per-function and MSVC-clean but license-incompatible. `Mr-Wiseguy/N64Recomp` (MIT, 8,266 ★) has the right architecture — per-function C through a `Generator` interface, TOML `{name, vram, size}` symbol input, delay-slot duplication, likely-branch skip labels, jump-table switches, `LOOKUP_FUNC` dispatch, MSVC/clang/gcc output, runtime in a separate repo — and no PS2 semantics at all.
**Decision.**
1. `recomp/p3fes_recomp` is written by us, modelled on N64Recomp's `recompilation.cpp`/`cgenerator.cpp`: one C++ function per IDA function (chunk-aware for the 172 multi-chunk functions), input = `symbols/functions.json` + the ELF, output against `runtime/include/p3fes/ee_context.h`. Decoder: rabbitizer's R5900 tables (MIT) if a census pass proves them complete on our MMI/COP2 instructions, otherwise our own table (`ps2-web-recomp/recomp/r5900.cpp`, 254 lines, is the reference). No N64Recomp *code* is copied beyond patterns; if any is, MIT attribution is added.
2. R5900 semantics (MMI, FPU, COP2 macro, SA, HI1/LO1) and runtime models (kernel HLE, IOP kernel/libs, SIF, DMAC/VIF/GIF, VU1 interpreter, IPU, SPU2, SIO2, CDVD) are **ported from `ps2-web-recomp` @ `c0f476e` under MIT attribution** (`THIRD_PARTY_NOTICES.md`; Play! BSD-2 notice with IPU tables), adapted to our interfaces (`EEMemory`, D3D11 `gs_backend.h`, XAudio2 `spu2_backend.h`, sector-level CVM CDVD per ADR-0008). Each ported unit lands only with compiled R5900 test vectors (ADR-0006 §5) or a `tracediff` pass; nothing is trusted by reading.
3. `ps2-web-recomp` is additionally built unmodified under WSL2 (per `fes-pc-recomp/docs/windows-build.md`) as a **second oracle** for Phase 4, pinned to a recorded commit, in gitignored `tools/third_party/`. Divergences are triaged in the order PCSX2 > ps2-web-recomp > us.
4. `ran-j/PS2Recomp`, `god-of-war-recomp`, `p3fes-recompiled` and PCSX2 sources are **never opened alongside `recomp/` or `runtime/`**; their commit logs and `stubs`/`keep_guest` lists are consulted as a pitfall checklist only (`docs/COMMUNITY.md` §2).
5. ADR-0003's compiler stance is unchanged: generated code and runtime compile under cl.exe and clang-cl; SIMD via `<immintrin.h>` intrinsics or portable lane loops, never GNU vector extensions or `musttail`.
**Why not alternatives.** Building on `ps2-web-recomp` would make clang-cl primary, lock Phase 5 to 16 KiB units, inherit a WebGPU/SDL host we must discard, and tie us to a ten-day-old single-maintainer codebase changing daily; forking it is more maintenance than porting its facts. `PS2Recomp` is GPL-3.0 and its P3FES derivative carries snaku's unlicensed map. From scratch forfeits a proven emitter architecture and the only MIT, game-proven PS2 semantics for no benefit. The hybrid (A now, C later) was offered and declined: two codebases to keep in sync for the most total work.
**Consequences.** `recomp/` gains a decoder, a chunk-aware function walker, a `Generator`-style emitter and semantic headers; `runtime/` grows subsystem by subsystem with a provenance line per ported file. First measurable milestone: all functions emitted and compiled under both compilers with `start`…`main` executing to `SetupThread` under `tracediff` against PCSX2. Phase 4 gets two oracles. Revisit if (a) ps2-web-recomp gains an MSVC/D3D path and per-function hooks, or (b) rabbitizer's R5900 coverage proves incomplete and the decoder cost dominates.

## ADR-0011 · 2026-10-18 · The recompiler decodes raw words with our own R5900 table; rabbitizer, binutils and `ps2-web-recomp` are decode oracles, not dependencies
_Resolves the deferred clause of ADR-0010 §1; adopted from the draft in `docs/DECODER.md` §3 after the full-binary census._
**Context.** ADR-0004 fixed IDA as the boundary/name authority and ADR-0010 §1 deferred the decoder choice to an instruction census. The census (`docs/ANALYSIS/08_instruction_census.md`) decoded all 1,194,277 words inside the 14,420 IDA functions: 199 base mnemonics, 0 invalid, VU0 used only as a vector ALU (no `vcallms`, no VU memory ops, no `bc2*`), likely branches only in SDK/MW/CRI library code. IDA's own decoder is unusable for instruction identity (opaque `cop2`, `mfthc1`/`pexow` misnamings, macro fusion of 16,389 words). rabbitizer @ `724a49a` (v1.16.2, MIT) names every one of the 199 (3 naming-only differences) but is a 610-ID multi-ISA C11 library whose R5900 mode inherits non-EE opcodes from its generic tables and whose build is Makefile-only with minimal MSVC provisions; `ps2-web-recomp/recomp/r5900.cpp` (MIT) is a 254-line field-oriented table that rejects non-EE words. A table of that shape in `tools/ours/ida/insn_census.py` already matches binutils on all but 8 explained words (`vsqrt`).
**Decision.**
1. `recomp/` gets `r5900_decode.{h,cpp}`: an `enum class Op`, `constexpr` lookup arrays by major opcode / `funct` / `rs` / `sa`, and an `Insn` with field accessors (`rs/rt/rd/sa/fd/dest/bc/imm`, delay-slot and likely flags), in the layout of `ps2-web-recomp/recomp/r5900.cpp` (attributed in `THIRD_PARTY_NOTICES.md`). **The `Op` set is census-scoped**: exactly the base mnemonics observed in the binary (198 — the census prose said 199; the JSON has 198) plus `Invalid`; EE instructions the game never uses (`dadd`, `tge`, `bltzal`, `pref`, `vcallms`…) also decode to `Invalid` until a census re-run justifies widening, which is a one-word, tested change per op. The recompiler **stops** on `Invalid` inside a function body (fail closed); `pmfhl` and `sync` are single ops with the format read from the field; `qmfc2`/`qmtc2`/`cfc2`/`ctc2` carry the interlock bit as a field.
2. The recompiler reads instruction **bytes** from the ELF at IDA's chunk ranges (`functions.json` + chunk list); it never consumes `ida_ua.decode_insn`, IDA mnemonics or item sizes. IDA's data items inside chunks (1,553 words — each would also decode as a valid instruction, so their nature must be settled per site before they are skipped) are handled by address, not by re-decoding.
3. Decode acceptance test (Phase 3 local gating): every function word is decoded by our table, by rabbitizer (Python, pinned 1.16.2 / `724a49a`) and by ps2dev `objdump -d`; the test fails on any disagreement not in the explicit alias list (`move`/`li`/`nop`/`b`/`beqz`…, `qmfc2`↔`qmfc2.ni`, `sync`↔`sync.l`, binutils' `vsqrt` gap). `insn_census.py --from-cache --objdump` is the prototype.
4. Jump tables come from `symbols/jumptables.json` (IDA `switch_info_t`, 553 sites, all 32-bit absolute, verified against the table bytes); the 15 unresolved `jr $v0` tail calls and all 5,143 `jalr` go through `LOOKUP_FUNC`.
**Why not alternatives.** rabbitizer as a submodule: complete but shaped for disassembly, C11/Makefile against ADR-0003, accepts non-EE opcodes; its benefit (names) is reproduced by a small table provable equivalent on the whole binary. Vendoring its `.inc` tables drags in descriptor machinery for fields we write directly. IDA's decoder: ruled out by the misrenderings. Porting `r5900.cpp` verbatim: acceptable, but we would re-type it into our `Op` enum anyway — we take the layout and the attribution and own the text.
**Consequences.** `recomp/` owns one more small, fully tested file; the three-oracle test gates `recomp/` locally; MMI/FPU/VU0 *semantics* remain ported from `ps2-web-recomp` (ADR-0010 §2) and are tested separately against PCSX2 (Phase 4). Revisit if the port ever needs instructions outside the 199 (a census re-run would show it first) or if rabbitizer gains an MSVC/CMake build and an emitter-oriented API.

## ADR-0012 · 2026-10-18 · Phase 4 oracle: PCSX2 is a *state* oracle (PINE + save states + GS dumps); per-instruction tracing comes from a second runtime, not from PCSX2
**Context.** With the user's BIOS in place, PCSX2 2.8.2 boots `SLUS_216.21` to the title (`docs/PCSX2.md`: BIOS `USA v02.30`, ELF CRC `94A82AAA`, `EntryPoint 0x00100008`, 15 IRX loads in topic 12's order, `NTSC 640x448 @ 59.940 Interlaced (FIELD)`, FPS 30 / VPS 60). PINE works (`pine.py`: reads of EE virtual addresses resolve through the guest TLB; `0x5E5150` returns the `#DirLst#` header byte-identical to the ELF). Save states (`.p2s`, zstd-per-entry zip) extract to a 32 MiB `eeMemory.bin`; at the title screen the code band `0x100000–0x5A1400` has **0 differing bytes** and the 149 directory tables are identical. But `[EmuCore/TraceLog]` produces **no per-instruction, syscall or hardware lines** in this release build (recompiler or EE interpreter), so `docs/TRACE_FORMAT.md §6` option (a) is unavailable. GS dumps (`Shift+F8`, `.gs.zst`, built-in replayer) exist.
**Decision.**
1. **PCSX2 is the Level B/C oracle.** `tracediff` compares *memory-write effects* and *control-flow checkpoints*: at every `SYNC` point (syscall, VBlank, frame flip — `docs/TRACE_FORMAT.md` §2) our runtime's EE RAM is diffed against a PCSX2 save state or PINE snapshot taken at the same point (PINE `MsgSaveState` driven by `tools/ours/pcsx2/pine.py`; extraction by `extract_savestate.py`). GS dumps from PCSX2 are the reference input/output for the GS → D3D11 backend.
2. **Level A (per-instruction) comes from a second runtime**, in this order of preference: (i) `ps2-web-recomp` built unmodified under WSL2 as ADR-0010 §3 already planned (its probes/watchpoints give per-instruction access), (ii) an interpreter-hook fork of PCSX2 kept **outside this repository** as a tool only (GPL code never enters `p3fes-port`; ADR-0009 §3 / ADR-0010 §4 stand), (iii) nothing — Level B has to localise the bug. The `P3TR` format is unchanged; only the PCSX2 emitter row becomes "snapshot-based".
3. **Determinism knobs recorded in `docs/PCSX2.md`** (software renderer, fast boot, MTVU off for state captures — PCSX2 warns states may be unstable with MTVU) are part of the oracle's definition; a reference capture names the ini it was taken with.
**Why not alternatives.** Patching our own PCSX2 for Level A first would spend Phase 4 time on GPL tooling before Phase 3 has anything to compare; Level B/C already localises most classes of recompiler bugs (wrong store address/value, wrong branch) to a sync interval, and the second oracle covers the rest.
**Consequences.** `tools/ours/tracediff` gets a snapshot mode (two `eeMemory.bin` + a mask file) before a stream mode. The first reference captures to take: post-`SkyStart` first flip, Atlus logo, title — each with its GS dump. Q-01 (kernel INTC chain semantics) is answered empirically by PINE polling of the RW flip counter vs VBlank count rather than by tracing.

## ADR-0013 · 2026-10-18 · Execution model: one host thread, a Win32 fiber per guest thread, virtual time from emitted cycle counts, interrupts delivered at check points
**Context.** The emitter is complete (`8e567bc`: 14,486 functions, host call/return for control flow, `$ra` written for tracediff) and the EE kernel's rules are known from the BIOS (`docs/ANALYSIS/15`): a strict-priority FIFO scheduler that switches threads *inside* positive syscalls, `i*` forms that only flag a reschedule taken at interrupt exit, handler chains that run with interrupts disabled and stop on a negative return, and hardware events (VBLANK_START, timers, DMAC completion) that the game observes through INTC/DMAC handlers and polled registers. Phase 4 compares our EE RAM against PCSX2 save states at sync points (ADR-0012), which needs runs to be reproducible byte for byte. The runtime has one `EEContext` (the CPU) and recompiled functions take `EEContext&`.
**Decision.**
1. **One host thread runs all guest code; each guest thread is a Win32 fiber.** `CreateThread` allocates a fiber (host stack for the recompiled frames; the guest stack is in guest RAM as on hardware); a kernel-initiated thread switch saves the CPU state into the outgoing TCB, loads the incoming one into the single `EEContext`, and `SwitchToFiber`s. The kernel's queue rules (`15` §3–4) are reproduced literally; no locks, no host scheduler, deterministic.
2. **Virtual time, not wall time.** The emitter adds each basic block's instruction count to `EEContext::cycles` (one add per block; 1 cycle/instruction is the first estimate, to be re-weighted from PCSX2 measurements). The kernel/timing HLE derives H-lines, fields and VBLANKs from it (EE 294,912,000 Hz; NTSC 15,734.26 H-lines/s, 262.5 per field, 59.94 fields/s). Interrupts, timer events and DMA completions are **delivered at check points only**: function entries and loop back-edges (`rt::check_events`, one compare when nothing is due), syscalls, and hardware-register accesses. Handler chains run as nested host calls on the current fiber (the real kernel runs them on a user-mode trampoline stack; ordering and the stop-on-negative rule are what matter). A preemption flagged by an `i*` call is taken at the end of the check point. When no thread is ready, the kernel advances virtual time to the next event instead of spinning (the idle thread).
3. **Ownership.** `runtime/hle/kernel/` owns the scheduler, syscall dispatch, INTC and timers, the DMAC register block and tag chains (data paths delegated per channel), the SPR channels, the time base, the `HwBus` and the `RtHooks` implementation (`runtime/include/p3fes/hle/hw_bus.h`, `runtime/include/p3fes/rt_hooks.h`). `runtime/rt/` (the adapter behind `recomp/include/p3fes_recomp_rt.h`) owns register semantics and guest RAM access and models no device; hardware windows go to `hooks().bus()`. `runtime/gs/` owns GS privileged registers, GIF, VIF1 and DMAC channels 1–2; `runtime/hle/sif/` owns the SIF registers, DMAC channels 5–6 and the IOP RPC servers (over `runtime/hle/` CDVD). DMA transfers run synchronously inside the DMAC owner at check points.
4. **Determinism rule.** Nothing on the guest path reads the wall clock or depends on host thread timing; the host frame loop presents whenever the GS flips. `--headless --snapshot-at <point>` dumps `eeMemory.bin` in PCSX2's physical layout for `tracediff snapshot`.
**Why not alternatives.** One OS thread per guest thread (the N64Recomp/Zelda64Recomp model) needs locks and makes interleavings nondeterministic, which defeats the snapshot oracle. C++20 coroutines cannot switch the deep host stacks of recompiled frames. Delivering interrupts only at syscalls would hang pure memory-poll loops (`sceCdSync` polls `sceCd_c_cb_sem`); per-instruction checks would cost more than the recompile gains. Cycle-accurate timing is out of scope; block counts are deterministic and proportional to work.
**Consequences.** `EEContext` gains `u64 cycles`; the emitter gains block cycle accounting and entry/back-edge `check_events` calls (on by default); `EEMemory::is_hw` becomes true for `0x10000000–0x1000FFFF` and `0x12000000–0x12001FFF`. Hot-path cost: one add per block, one compare per entry/back-edge — to be measured against the title-screen flip rate. Fibers are Windows-only, which matches the target (GOAL.md: Windows x64).

## ADR-0014 · 2026-10-20 · Sound effects: run the game's own SK/libsd IOP modules on a small R3000 interpreter inside the IOP HLE, driving a host SPU2 voice model ("B-lite")
**Context.** After Milestone 4 the only sound missing is the sequenced-kit path: BGM and voice are CRI ADX streams (already mixed by the ADXI model), but every sound effect goes through the Standard Kit — `H_Sndcom_PlayVoice 0x10DB60` (512 call sites) → `SESQ_Control(port, 0, 10, group, entry)` over SIF RPC — and the behaviour behind that thin command stream lives in six IRX modules on the disc (SDRDRV, SKSOUND, SKHSYNTH, SKSESQ, MODSESQ, MODHSYN: 80,592 bytes of MIPS-I text, a 240 Hz tick, a 35-opcode SE interpreter, a synth module that keys SPU2 voices through libsd). The port has no IOP CPU; `runtime/hle/sif` answers the RPCs with constant replies. There is no sequenced music in this game (the MIDI bank is never requested, MODMIDI never loaded). Study: `docs/ANALYSIS/19_spu2_sequenced_sound.md`.
**Decision.**
1. **Interpret, don't re-derive.** The six modules are loaded at run time from the user's `extracted/disc/LIB31/` image (as the ELF is; nothing copied into the repo), relocated into the 2 MiB IOP RAM model, and executed by a small R3000 (MIPS I, no FPU/COP2) interpreter inside the IOP HLE. Their ~40 kernel imports (thbase, thsemap, timrman, intrman, sysmem, loadcore, sysclib, stdio) and the 20 libsd functions are HLE'd; libsd drives a host SPU2 voice model (48 voices: ADPCM, ADSR, pitch, L/R volume; reverb optional) summed with the PSM/ADX output into the existing `AudioSink`.
2. **Virtual time stays the clock** (ADR-0013): the interpreter runs only at RPC calls and at the tick deadline (4,167 µs of virtual time); `GetSystemTime` is served from EE cycles / 8; the output is a pure function of the request stream, so snapshots and the audio fingerprint stay deterministic.
3. **MIT reference code may be ported with provenance lines** (ADR-0010 §2): `ps2-web-recomp`'s R3000 interpreter, IOP kernel/library HLE and SPU2 voice model are the permitted sources; GPL PCSX2 is never opened.
4. **Milestones on the recorded dorm route** (study §4): (0) `--sound-log`; (1) the stack runs silently with M1/M2/M4 frames identical and `eeMemory` differing only in the SK-id class, bank bytes in voice RAM equal to the `.BD` files and PCSX2's `SPU2.bin`; (2) first key-on non-silent at the memory-card prompt; (3) menu and text-advance SFX audible with no stuck voices; (4) battle bank, balance, reverb.
**Why not alternatives.** An own sequencer at the RPC boundary (A) costs the same reverse engineering and can never be shown right; a full IOP emulator (B) re-hosts the whole `runtime/hle/sif` and the port's speed budget; hand-decompiling MODSESQ/MODHSYN (C, ~15k words) has no oracle until B-lite exists — it becomes Phase-5 work *after* B-lite, with the interpreter as the pair-test oracle.
**Consequences.** New `runtime/hle/sif/iop/{r3000,irx_loader,iop_kernel_hle,libsd_hle}`, `runtime/audio/spu2_voice.*`, an IOP clock in `iop_core.h`; contract rows I-11/L-31/L-32 become model rows plus I-11a (the tick); the M4 tracediff "sound-command rings" class shrinks because SK ids become MODSESQ's real ones. Lead decision, reversible at milestone 1 if the loader/kernel semantics cost more than the study's first-week estimate.

## ADR-0016 · 2026-10-24 · Mods overlay: whole disc files replaced from host folders by a virtual disc at the DiscSource layer, off unless `--mods` is given
_(ADR-0015, the editor, lives on the `editor` branch; this is the next free number.)_
**Context.** The editor round (ADR-0015) needs every message box and texture editable *outside* the ISO, saved as files that survive a restart and reload live. The game learns where a file is in three places: the CVMs' disc LSN and size from `sceCdSearchFile` at boot (`dvCiOpen 0x55A1F0`, cached by dvCi; `size_sct = (size + 2047) >> 11`, and `dvCiSeek` clamps every read to it); a CVM member's ISO LBA and size **only** from the 149 CRI ROFS `#DirLst#` tables compiled into the ELF (`docs/ANALYSIS/11_file_io.md` §1: ROFS runs with external directory records and never reads a CVM's directories); and everything else (AFS / PAK / BIN member tables) from inside the files themselves.
**Decision.**
1. **Folders mirror the disc** (`<mod>\DATA\FIELD\X.PAC` = DATA.CVM's `\FIELD\X.PAC`, `BTL\`, `BGM\`, outer `LIB31\`), names matched case-insensitively like `iso9660::component_matches`. Only existing whole files are replaced; the editor rebuilds a whole PAK. SYSTEM.CNF, the boot ELF and whole CVMs are refused, as are paths escaping the root (`..`, absolute, drive / stream names, reparse points and symlinks under the root) and files above a size cap (1 GiB). A `--mods DIR` is one mod or a folder of mods (optional `mod.json`: name, description, `load_order`); several `--mods` stack, later wins per file.
2. **`ModsOverlay : DiscSource`** (`runtime/hle/mods_overlay.{h,cpp}`) wraps the user's ISO or extracted volumes. Every CVM is **relocated** to its own window after the real image (`0x400000 + i·0x400000`) and reported with the largest size dvCi can address (`0xFFFFF800` B): BTL.CVM at LSN 633 cannot reach past the real image otherwise, and a fixed size lets reloads add extents without touching dvCi's boot-time cache. Each replaced file gets a new extent at the end of its window; reads there come from the mod file, all other sectors from the base. Patched in the virtual sectors: the outer PVD volume size, the outer root records of the CVMs and the records of replaced outer files, the CVM header sizes (CVMH +0x1C, ZONE +0x04 / +0x30, moved by the same amount), the inner PVD volume size and the inner directory records of replaced members. `find_file` (cdvdfsv's search) answers with the relocated / replaced extents. Patched in **guest RAM** (the ELF is loaded from a host file, not from disc sectors): the ROFS table entries of replaced members (`patch_rofs_tables`, right after the ELF load and after every reload; a table is matched to a CVM only when its whole listing equals that CVM's directory at the table's LBA, since DATA and BTL share directory LBAs). Path tables hold directories only and are unchanged.
3. **Off by default.** The overlay exists only with `--mods DIR` (`p3fes`) / `HostConfig::mods` or `HostConfig::mods_overlay` (the editor). Without it `GameHost` keeps the plain source: the same code path as before, proven by the replay gates (frames, eeMemory, gsMemory unchanged). With it, machine states carry `mods=<fingerprint>` in their configuration.
4. **Reload** (`GameHost::reload_mods`, `set_mods_enabled`, `set_mod_folders`): re-scan; unchanged files keep their extent, changed ones get a new one; extents are never reused, and files up to 32 MiB are kept in memory, so a ROFS handle opened before the reload reads exactly the bytes it opened (larger files are read from the host file at each read; the overlay never holds a mod file open). The RAM tables are rewritten at once (removed overrides restored), so the next open sees the new file; files H_Cdvd has already loaded stay until the game loads them again. `mod_files_read_since_reload()` / a read callback and `mods_stale_after_reload()` tell the editor which changes need a scene reload. Every applied override is logged (path, mod, size, LSN) at start and after each reload.
**Why not alternatives.** Hooking `RFDIR_SearchName` / `RFMAI_OpenG` at the path level: touches recompiled game code and still needs the ROFS tables right for `ADXF_GetFsizeSct`. Extents inside the real image or in place: no room for grown files, and BTL.CVM's window ends inside the image. Rewriting a copy of the ISO: what the user asked us not to do. Replacing PAK members in the engine: the editor already owns PAK building, and whole-file replacement covers every internal table for free.
**Consequences.** With `--mods`, the game's CD reads go to relocated LSNs (guest RAM holds them in dvCi handles), so `--mods` runs are never compared with the no-mods references; a file can be replaced, never added (the ROFS tables are fixed size); a window holds ~2^21 sectors minus its CVM (DATA.CVM: ~0.9 GB of extents per session, restart to compact). Tests: `tests/hle/test_mods_overlay.cpp` (synthetic disc with a CVM, every untouched sector compared; the real disc end-to-end through `CdvdHle` and the ELF's own tables).

## ADR-0017 · 2026-10-30 · Modernize pass: native layers behind per-layer switches, files first, instant loading
**Context.** The Journey's faithful decomp replaces every one of the 14,500 functions, but the game still runs on emulated PS2 hardware (CDVD, IOP / SIF, SPU2, IPU, GS, VU1, DMAC, INTC, timers). The user's goal is a fully native game with no PS2 emulation, with the platform removed *before* the hand-written lift, so the lift never rewrites PS2 glue.
**Decision.** Plan and checks: `docs/MODERNIZE_PLAN.md`.
1. Each PS2 layer gets a faithful / native switch (`HostConfig::native`, `--native`). It is off by default until its checks are green. The swap point is the game's own wrapper, never the hardware register.
2. Order: baseline tag `journey-100` → disc and files → input → sound → movies → graphics (alongside, as that work exists) → kernel and timing. Emulated devices are deleted last, with the user's agreement.
3. Native file loading completes **at once** (user, 2026-10-30), not on the emulated drive's schedule. The user re-records the replay routes for the native configuration; the old six routes keep gating the all-faithful configuration byte-exactly.
4. Each layer has its behavioural check against the faithful path (identical bytes read, identical pad work area, bit-exact decode and a stated mix tolerance, bit-exact movie frames, frames identical to the software GS while exact).
**Consequences.** The lead gate runs two configurations until the faithful devices are removed. `EEContext` stays as the calling convention of the game functions; removing it is the lift pass. With native files, the mods overlay (ADR-0016) becomes a lookup by path.
