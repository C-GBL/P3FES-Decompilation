## 0. Headline

* **Task tree.** Every UI screen is a `kwlnTask` (`kwlnTaskCreate 0x194B20(parent, name, priority, update, destroy, work)`; work pointer at task `+0x3C`, `kwlnTaskGetWorkData 0x195540`; state nibble at `+0x1C`, `kwlnTaskGetState 0x195290` returns it and the parents poll for **3 = finished**; an update callback returns 0 to continue and −1 to finish). The camp (pause) menu root is **`H_Camp_CreateDrawTask 0x11A770`** ("H_CampDraw", created by `K_FldEvent_UpdateFldEventTask 0x1C8620`) whose update **`H_Camp_UpdateDrawTask 0x11A050`** is a 21-state machine (`jpt 0x7B5420`) that owns one child screen at a time: the main list **`H_Camp_UpdateRootDrawTask 0x11B420`** ("H_CampRootDraw") and, by selected index, **Skill → `H_Camp_CreateNewCampSkillDrawTask 0x1617D0`, Item → `H_Camp_CreateNewItemTask 0x14EE80`, Persona → `H_Camp_CreateCampStatusPersonaDrawTask 0x1336B0`, Equip → `H_Camp_CreateSoubi1DrawTask 0x130F20`, Status → `H_Camp_CreatePcStatusRootTask 0x123570`, S.Link → `H_Camp_CreateComuDrawTask 0x136750`, System → `H_Camp_CreateSystemMenuDrawTask 0x1548A0`** (§2). All of it is `sub_*` in the committed symbols.
* **2D drawing is RenderWare Im2D, not GS code.** Sprites (`sprDrawSprite 0x1127D0`), the cursor quad (`H_Cursor_UpdateDrawTask 0x100230`) and glyphs (`frFontRasterDrawGlyph 0x3B38F0`) all fill `RwIm2DVertex` arrays and call the function pointers `dword_960090` (= `RwRenderStateSet`, obs from the `(rwRENDERSTATETEXTURERASTER, raster)` pairs) and `dword_9600A0` (= `RwIm2DRenderPrimitive(4 = tri-strip, verts, 4)`), with `flt_960088` as the near screen z. The `G3_2DFont_Node.c` band (`PS2FontNode2d 0x470200`) is the RW PDS pipeline that turns those into the `rt2d_font` VU1 packets of topic 14 — the UI never touches GIF/VIF itself (consistent with topic 10).
* **Font renderer + `.FNT` verdict (resolves the Phase 1 open item).** `frFontSystemStart 0x3B4EE0` (from `kwlnInitMain`) → `frInitFontTable 0x3AF7A0` → `frLoadFontData 0x3AFC70` loads exactly one file, **`font/font0.fnt`** (`0x6A2820`), as style 0 and copies it into styles 1–5; style 8 is bound per message by `sub_3B19A0` (the BMD-side font slot of topic 18 §5.3). The glyph index of a text code is `c < 0x80 ? (c == 0x20 ? 0x1F7 : c − 0x20) : (((c − 0x8080) & 0xFF00) >> 1) + ((c − 0x8080) & 0x7F)`, clamped to the replacement glyph `0x147` when ≥ the file's glyph count (`sub_3B0620 0x3B06D8–0x3B074C`, obs). The file is a 32-byte header, a 16-entry CLUT, a proportional-width table (two `s8` per glyph) and **Huffman-coded 4-bpp 32×32 bitmaps** decoded by `sub_3B47B0` into 512-byte buffers that are uploaded to a pool of 256 `RwRaster(32, 32, 4, 0x4504)` glyph slots. The decoder was re-implemented on the host from the instructions and reproduces exactly 512 bytes per glyph on `FONT0.FNT` and 288 on `FONT3.FNT` (§5.3). There is no separate glyph map: the two-byte codes `80 80 … 83 FF` map linearly onto the FNT's glyph order, PersonaEditor's index is ours + 0x20. `FONT1–3.FNT`, `SYSFONTALL.FNT`, `ADVFONTALL.FNT` are not referenced by the ELF (no string; `SYSFONTALL`/`ADVFONTALL` have a different magic `66 A3 31 01`).
* **Date/time HUD data sources.** One `s16` at **`0x83679C`** = days since April 5 (`datGetDaysSinceApr5 0x16EF20` / `datSetDaysSinceApr5 0x16EF70`) and one `u8` at **`0x83679E`** = day part (`datGetTime 0x16EF30`). Month/day are recomputed on every use from the month-length table **`0x5E3B60`** (`clndGetMonthFromDaysSinceApr5 0x17D830`, `clndGetDayOfMonthFromDaysSinceApr5 0x17D9C0`, inverse `clndGetDaysSinceStartFromDate 0x17D8B0`), weekday = `(days + 7) % 7` with **0 = Sunday** (`clndGetWeekDay 0x17DAE0`), moon phase from the 368-byte table **`0x5E38D0`** (`clndGetMoonPhase 0x181B50`, `0x0E` = full moon). The HUD is the task pair **"H_DayPartsDraw" / "H_DayPartsPos"** (`H_DayParts_CreateTask 0x184DB0`, drawn by `sub_1842C0`) from `camp/i_moon_00.spr`; its **"Next: N"** is the distance to the next `0x0E` in the moon table (§3.3) — on 4/7 (day 2) the table reads `0C 0D 0E`, so the dorm scene shows "Next: 2" and "Tu" (`(2 + 7) % 7 = 2`).
* **Table readers.** Battle `.TBL`s are loaded at init by `sub_27DE40` over the 8-record list `off_692D40` (`battle/SKILL.TBL`, `UNIT`, `MSG`, `PERSONA`, `ENCOUNT`, `EFFECT`, `MODEL`, `AICALC`, each with a `_F` variant for The Answer; §6); `event/itemtbl.bin` is `memcpy`'d whole into `0x83BB30` and sliced into 14 section pointers by `sub_16C2F0`; the UI's own tables are the `.PAK`s of `camp/` (`camp/ptypnl.pak`, `camp/areapnl.pak`, `camp/camp_*.pak`) registered through `H_Cdvd_CacheAddArchive` (topic 11 §2) and read as `.SPR`/`.TMX`/`.ANM`.
* **Opening prompts.** The Journey/Answer choice is `H_FileSetup_UpdateChoiceDataFileSetupTask 0x192B50` (debug-text prompt through `H_Dbprt_FmtAt`, confirm = `gPadFlags & 0x40`), the carry-over ("played before") flow is `H_FileSetup_UpdateHikitugiDataProcTask 0x193020` over the memory-card window tasks (`Y_Misc_CreateMcTasks 0x420340`), the boot-time card check is `clndUpdateBootupCheckMemcardTask 0x188690` → `Y_Misc_CreateMCWNDProcTasks 0x4214E0` ("mcWNDProc") with `H_Memcard_*` (§7).

Confidence: **high** for §2–§5 (every statement read from the instructions; the FNT layout verified against the files), **medium** for §6–§7 (loaders read, consumers only skimmed).

## 2. The camp menu task tree

### 2.1 kwlnTask facts used by every screen (obs)

`kwlnTaskCreate 0x194B20` = `kwlnTaskInit 0x194C50(name, priority, update, destroy, work)` + `kwlnTaskAddChild 0x195550(parent, task)`. The task record keeps the work pointer at `+0x3C` (`kwlnTaskGetWorkData 0x195540`, `SetWorkData 0x195530`), a frame timer at `+0x28` (`kwlnTaskGetTimer 0x195520`) and a state word at `+0x1C` whose low nibble `kwlnTaskGetState 0x195290` returns when the task still exists (`kwlnTaskExists`), asserting `"Process stat Invalid!!"` for values other than 0–3; every parent in this layer waits for **3** before it destroys or re-creates a child (e.g. `0x11A454`, `0x183638`, `0x192D7C`). Update callbacks receive the task in `$a0`, fetch the work through `+0x3C` and return 0 (keep running) or −1 (done: `0x11A404`, `0x100544`).

### 3.2 Arithmetic (obs; all 16-bit, the compiler re-truncates after every step)

* `clndGetMonthFromDaysSinceApr5 0x17D830(days)`: `rem = (s16)(days + 4); month = 4; while (rem >= len[month−1]) { rem −= len; month = month == 12 ? 1 : month + 1 } return month` — i.e. day 0 is **April 5**; `clndGetDayOfMonthFromDaysSinceApr5 0x17D9C0` returns `rem + 1`; `clndGetCurrentMonth 0x17D920` / `clndGetCurrentDay 0x17DA40` are the same loops on `datGetDaysSinceApr5()`.
* `clndGetDaysSinceStartFromDate 0x17D8B0(month, day)`: sums `len[4−1], len[5−1], …` while counting `month` down to 4 (0 wraps to 12), then `+ day − 5`; May 1 = 26, January 1 = 271 (der). A month ≤ 0 never terminates within 2³² steps (no caller passes one).
* `clndGetWeekDay 0x17DAE0(days) = (days + 7) % 7` through `div`/`mfhi` (negative days give a negative remainder); `clndGetCurrentWeekDay 0x17DB00` applies it to the current day. **0 = Sunday** (`clndIsHolidayOrSunday 0x17DD20` treats remainder 0 as a holiday; `sub_185B40 0x185D0C` colours weekday 6 = Saturday blue), so April 5 is a Sunday and 4/7 is "Tu".
* `clndIsDateInRange 0x17E480(m0, d0, m1, d1)` and `…FromStart 0x17E5D0(m, d, n)` compare day counts (an `n` of 0 logs `"Calender chk range is 0 "`).

### 4.2 `H_Cursor` (obs)

`H_Cursor_CreateTask 0x1005B0(parent, {x, y} packed in $a1, const float rect[4] in $a2, u32 rgba in $a3, float z in $f12)` allocates the 0x150-byte work (`HCursorWork`, `game/include/p3fes/game/ui.h`), creates "H CURSOR Draw" (priority 0x18BF, update `H_Cursor_UpdateDrawTask 0x100230`, destroy `0x100580`) and stores pos (`+0x114/+0x118`), rect (`+0x11C..+0x128`), z (`+0x12C`), the colour four times (`+0x130..+0x13F`) and `should_draw = 1` (`+0x140`). ### 5.1 `.SPR` files and the `spr*` layer (obs: `sprFileHandleUpdate 0x112110`, `sprCreateHandle 0x1158B0`, `sub_1126B0/0x112740`, `sub_238FD0`)

A sprite file handle is 0x1C0 bytes (`sprAddFile 0x112370(path)`: `RwHeapCalloc`, name at `+2`, linked at `gp-0x4DB0`); `sprFileHandleUpdate` runs it through states **0** `H_Cdvd_Request(name)`, **1** header: the 32-byte SPR header is copied to `+0x198` (`u16 +0x1AC` = texture count, `u16 +0x1AE` = sprite count), **2** per texture an 8-byte `{u32, u32 offset}` entry → `uttmxCreateRaster(file + offset)` (a TMX → `RwRaster`) stored at `+0x104 + 4*i`, **4** per sprite an 8-byte `{u32, u32 offset}` entry → 0x80-byte records copied into `RwHeapCalloc(count, 0x80)` at `+0x184`, **5** ready (`sub_111F30` = `state == 5`). `sprCreateHandleFromData 0x112420(data)` builds the same handle around an in-memory file (the PAK path: `sub_18BC80` `camp/ptypnl.pak`, `sub_18E4A0` `camp/areapnl.pak`). Sprite record fields used by the readers: `+0x14` texture index, `+0x54/+0x58` u0/v0, `+0x5C/+0x60` u1/v1 (texels; width = `+0x5C − +0x54`, `sub_1126B0`), `+0x74/+0x76` `s16` width/height overrides. A draw handle (`sprCreateHandle(list, file, sprite)`, 0x34 B) carries x `+0x10`, y `+0x14`, flags `+0x18`, inverse alpha `+0x19`, 12.4 scale `+0x28/+0x2A`, z `+0x2C`, rgb `+0x30..+0x32` (0xFF); `sprDrawSpriteBasic 0x1159F0 … Basic5 0x115DE0` create one, draw it with `sprDrawSprite 0x1127D0` (4,692 B: `RpSkyRenderStateSet`, Im2D) and free it; `sprSpriteDrawAll 0x1125D0` (from `kwlnRootUpdate2DDrawBeginTask`) draws the persistent list at `gp-0x4DB4`. `sprFontInit 0x111F50` (from `kwlnInitMain`) synchronously loads **`camp/font/i_font01a.spr`, `i_font02a.spr`, `i_font02b.spr`** into **`sSprFontFiles[3] 0x833A40`** (`sprFontGetFile 0x1120A0(i)`, 225 call sites): the sprite "fonts" of digits and symbols — `bp_ifont.c`'s `sub_238980` prints a number with `sprintf` and draws each digit as sprite `11 + digit` of font `i` through `sub_238FD0`; the HUD digits above are the same files.

### 5.2 Text → glyph nodes → quads (obs)

Per text run the layout helpers of `frFontEx.c` (`sub_3B2CB0`, `sub_3B2F90`, `sub_3B32D0`; 65/5/52 callers) call **`sub_3B0970`** (proposed `frFontBuildGlyphList(text, style, colour, flags, line)`): for each byte (two bytes when ≥ 0x80) **`sub_3B0620`** (proposed `frFontCreateGlyphNode`) pops a 0x2C-byte node from ring buffer 1 (`rbInitRingBuf(0x2C, 1024)` in `frInitFontTable`, `"FONT SYS : Text buffer overflow error."` when empty), stores code/style/colour, computes the glyph index (§0), creates or finds the glyph raster (**`sub_3B0430`**, proposed `frFontCacheGlyph`: cache hit → refcount `+4`++; miss → `RwHeapMalloc(0x200)`, `sub_3B4770`/`sub_3B47B0` decode (§5.3), `sub_3B3D60` takes a free 32×32 raster slot from the pool and `memcpy`s the 512 bytes into it (`frFontRasterCreate2 0x3B3F90` locks the raster and its palette), `sub_3B03A0` registers it in the GS-list container (`"FONT SYS : GS buffer over flow."`)), and sets the metrics with **`sub_3B01D0`**: size byte `gp-0x57F8[style]`, advance `+0xC` from the FNT width table when flag bit 0 (proportional) is set — `w = right − left` (+4 for `'!'`/`'1'`, +2 below index 0x1C6 else +3), `advance = w × size / 32`, x offset `−left × 16 × size / 32`, scaled by `gp-0x46B8`/`gp-0x46B4` (/128) — and the descender flag (`g j p q y Q` set bit 0x10 → `+0x8 = 16`). `frFontDraw 0x3B1360(line, skip)` then walks the nodes: `frFontRasterDrawGlyph 0x3B38F0(x16, y8, node, raster, w, h, rgba)` builds four `RwIm2DVertex` (x in 1/16 px, y in 1/8 px, z `flt_960088 − z`, rhw `1/camera->+0x80`, UVs from `dword_6A28D0`) and issues `RwRenderStateSet(1, raster)` + `RwIm2DRenderPrimitive(4, verts, 4)`. `frFontManUpdateTask 0x3B18C0` ages the raster slots every frame (`sub_3B3770`) and `sub_3B0030` releases a line's nodes back to the ring buffers.

### 5.3 `.FNT` format (obs from `frAddFontStyle 0x3AFAD0`, `sub_3B01D0`, `sub_3B0620`, `sub_3B4770`, `sub_3B47B0`; verified on `DATA/FONT/FONT0–3.FNT` with a host decoder, no game bytes copied)

| offset | field | FONT0 / FONT3 |
|---|---|---|
| `+0x00 u32` | header size (= 0x20) | 0x20 |
| `+0x04 u32` | unverified (0xEFC2 / 0x46BA; not read by the code seen) | — |
| `+0x08..+0x0B u8` | 1, 1, **CLUT blocks ×64 B** (`lbu +0xA; sll 6`), 0 | 1 1 1 0 |
| `+0x0E u16` | **glyph count** (`lhu +0xE`; the `>= count → 0x147` clamp, the `printf("… fontnum=%d")`) | 506 / 340 |
| `+0x10 u16`, `+0x12 u16` | glyph width, height (`sub_3B1A10/0x3B1A40`) | 32×32 / 24×24 |
| `+0x14 u16` | bytes per glyph (4 bpp) | 0x200 / 0x120 |
| `+0x16 u8` | 1 = the two length-prefixed tables follow the CLUT (`lbu +0x16`) | 1 |
| `+0x20` | CLUT: 16 × RGBA8, a grey ramp `00…F0` with alpha 0x80 | — |
| `+0x60` | `u32 size1` + **`s8 [count][2]` {left, right}** proportional widths (`size1 = 2 × count` in FONT0; style `+0x8/+0x10`) | 1012 B |

`sub_3B4770` resolves the three regions, `sub_3B47B0(dst, glyph, hdr, regions)` walks bits `offsets[glyph] .. offsets[glyph + 1]` (a 17-bit shift register with a sentinel bit refilled from the next `u16`) through the tree and appends one byte per leaf, returning the byte count (`gp-0x46A0`). Decoding glyphs 0, 1, 2 and the last of FONT0 and FONT3 on the host gives exactly 512 and 288 bytes; the offsets block has `count + 1` entries and the last offset equals the stream length in bits (`ida/logs` not needed — the probe is 40 lines of Python over the file header). `SYSFONTALL.FNT` / `ADVFONTALL.FNT` (`66 A3 31 01` magic) are a different, unreferenced format.

### 5.4 Lines, rows, tags and the raster-slot cache (obs; the Phase 5 font slice, `game/src/ui/font.cpp`)

* **Nodes.** A glyph node (0x2C B, ring 1) is `+0 u16 code`, `+4 s32 x offset` (1/16 px), `+8 s32 y offset` (16 for descenders), `+0xC s32 advance`, `+0x10 u32 rgba` (alpha in the low byte), `+0x14 u8 colour set`, `+0x15 u8 style`, `+0x16 u8 mode` (2 = fading), `+0x17 u8 flags` (from the default-flags word `gp-0x57F0`: bit 0 proportional, bit 4 descender), `+0x18/+0x19` scaled sizes, `+0x1C` the GS-list entry of its raster (what `frFontCacheGlyph` returns: the slot's `+0x10` on a hit, the new entry on a miss), `+0x28` next glyph. A line node (0x44 B, `frFontInitLineNode`) is `+0 u16 code`, `+2 u8 alpha`, `+3 s8 letter spacing`, `+4/+8 x/y` (1/16 px), `+0xC` glyph count, `+0x1C` first glyph, `+0x24` next line (the alpha/style/colour setters walk it), `+0x28` next line of the chain (the row helpers walk it), `+0x2C` the chain's first line (a fresh node points at itself), `+0x40` dirty flag.
* **Measuring.** A line's width is `Σ (advance + letter spacing)` over its glyphs (`frFontLineGetWidth`, proposed `frFontLineGetWidth`). A **row** of a chain is the run of lines, from a given line along `+0x28`, whose `y` is below that line's `y + 100`; `frFontChainGetRowWidth(row, chain)` returns the summed widths of the row starting at the `row`-th line, `<< 4`; `frFontChainGetRowPos` the `row`-th line's position; `frFontChainMoveTo(x, y, chain)` moves the chain so its first line lands on `(x, y)`; `frFontChainCentreAt(x, y, chain)` centres every row on `x` (`x − W/2 × 16`, `W` halved toward zero) with the first line's `y` on `y`; `frFontLineChainJoin(a, b, 1)` appends chain `b` after `a`, placing it at `a.x + a.count × 16`. `frFontChainCountLines` counts the lines (its inner row walk is dead). Line spacing `gp-0x5800` defaults to 25 (`frFontResetLineSpacing`); `frFontLayoutNewRow` steps a layout record down one row (`y += spacing × 8`).
* **Fading.** `frFontLineFadeStep` lowers the alpha of every mode-2 glyph by 8 (clamped at 0) and moves it down 16; it returns 1 while any glyph still changed.
* **Tags.** `frFontProcessTagEx(scan, tag)` walks the text from `scan->+0x18`: a byte `0xFn` and the next byte form a tag code; when it equals `tag` (non-zero) `sFrTagTable 0x6A2370[code & 0xFF](code, scan)` runs (`0x42` `frFontTagSetParams01`, `0x43` `frFontTagSetParams23`, `0x46` `frFontTagWait`, `0x47` `frFontTagWaitIfFlag389`; 0x4C entries); then `2 × ((code >> 8 & 0xF) − 1)` parameter bytes are skipped. A non-zero handler result or the codes `F131`/`F110`/`F104` stop the walk; other bytes ≥ 0x80 are two-byte glyphs. Before the walk a text whose first byte is no tag but whose second is 8 skips 4 bytes, and the low 6 bits of the tag-flag word `gp-0x5808` are cleared. A parameter is two bytes `(p0 − 1) | (p1 == 0xFF ? 0 : p1 − 1) << 8` (so no parameter byte is 0). `0x42`/`0x43` store two parameters each at `0x95ABE0..0x95ABEC` (read back by `frFontTagGetParam0..0x3AF390`); `0x46` makes the window (`scan->+0x14`) wait `max(0, (s16)p)` ticks (`+0x30` = code, `+0x3C` = ticks, `+0x38` = 1 when `+0x34` is set) and sets tag flag 0x80; `0x47` does the same only while flag 389 is set (`datGetFlag`), tag flag 0x40. `frFontProcessTag(text, window, tag)` runs the scan on a 32-byte record in its frame.
* **Raster slots.** The manager at `gp-0x46AC` keeps an active list (`+8` head, `+0xC` tail) and a free list (`+0x10`/`+0x14`) linked by slot `+0x18`; a slot is `+0 flags` (bit 0 in use), `+4 glyph`, `+8 s16 colour set`, `+0xA s16 ticks`, `+0x10` GS-list entry. `frFontRasterLookup` (via `frFontRasterFind`) finds `(glyph, colour)`, sets ticks to 1 and the in-use bit; `frFontRasterAgeSlots` (every frame) decrements the ticks of slots not in use or without a GS entry and moves those below zero to the free list's tail.
